# ppu-ocria-nano scope: decisions

Date: 2026-11-25

Context: LlamaIndex released OCRia-nano-1 on 2026-11-23. It is seven ONNX
models (line detector, script router, four CTC recognizers, LayoutNet) with
8.1M parameters in total. The reference runtime is LiteParse (Rust,
Apache-2.0). The weights, the charsets and the model metadata come under the
`ocria-nano-1-license` (modified AI Pubs Open RAIL-M). LiteParse ships no
Python reference for these models; the Rust code is the reference.

## Decided during the build

| #   | Question      | Decision                                                                                                                                                                                                                                                                                                                                                                                                   | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| --- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Q10 | Image input   | OCR runs on the decoded pixels. The page is `pixels x 72 / dpi` points (dpi from PNG `pHYs` or JPEG JFIF, else 150, as LiteParse `conversion.rs`). LayoutNet's 150 dpi raster is an area resample of the pixels, in PDFium's BGR channel order. This is LiteParse's own `ocr_page_images` path. It differs from `lit parse image.png`, which wraps the image in a PDF and OCRs a PDFium render at 250 dpi. | No PDFium for images, so React Native (Hermes has no WebAssembly) runs the same path as Node and browsers, and the goldens test that path exactly. Measured on 2026-11-25 against `lit parse <png> --format markdown` (same build, same models) on the 11 PNG fixtures: character similarity (difflib ratio) 0.955 to 0.999 on 9 pages, where the differences are single words and go both ways ("Spring Survey" read right here, "दौरा" read right by lit). The other 2 pages (vertical CJK, a 30 degree tilt) are unreadable on both paths. Upstream's ParseBench numbers come from the PDF path and are not re-measured for images. |
| Q11 | Golden method | A recorder patch on LiteParse `crates-v2.21.2` (`scripts/golden/`) writes every stage boundary of the OCR stage and of the full parse, for 10 PNG pages and 10 PDFs (3 generated with reportlab for headings, lists, tables, code, links and page chrome). Each TypeScript stage is tested on upstream's recorded input for that stage. Goldens are compact JSON, gzipped (2 MB).                          | A failure names the stage. The PDFs reach projection and layout code that OCR pages never do.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Q12 | Port shape    | `docs/PORTING.md`: one folder per Rust file, serde-shaped types, f32 through `Math.fround`, Rust semantics helpers in `src/ocria/rust.ts`, 300-line files.                                                                                                                                                                                                                                                 | Keeps each upstream sync a diff of the Rust.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

| Q13 | PDF engine | LiteParse's own patched pdfium: the `pdfium-emscripten-wasm.tgz` archive of `run-llama/pdfium-binaries` release `chromium/8172` (pdfium 160.0.8172.0; sha256 `10ed1da77f367493f307770552fed25e296ba64e603a4f2ba5cae7ec38ac9668`), linked by this repository's build into `pdfium.js` and `pdfium.wasm` with emsdk 3.1.72, the version that release was built with. Replaces the `@embedpdf/pdfium` peer dependency of ppu-indra-ocr. | User decision. LiteParse's extraction calls functions that stock pdfium lacks (`FPDFText_GetCharCode`, `FPDFText_GetCharInfoBatch`, `FPDFFont_GetCharGlyphName`, `FPDFFont_GetGlyphPathFromCharCode`), so only this build can match it exactly. |
| Q14 | PDF fonts | `convertPdf` passes the host's Arial, Times New Roman and Courier New to pdfium by default on Node, Bun and Deno (`hostFonts()`), and none in a browser. `fonts: []` turns it off. | Decided by the agent on 2026-11-25; the user can reverse it. A native pdfium substitutes these files for the standard-14 fonts, so with them the wasm build matches the macOS goldens exactly; without them boxes move by up to 0.6 pt (markdown unchanged on the 10 fixtures). Cost: PDF boxes depend on the host's fonts, as LiteParse's do. Verified on macOS only. |
| Q15 | Platform of exact parity | The recognizer-dependent goldens (engine results, image markdown, the scanned PDF: 25 tests) run exactly only on macOS arm64, the platform they were recorded on, in CI job "Golden parity (macOS arm64)". Linux CI skips them and checks two-column markdown similarity > 0.98 instead. Every other stage stays exact on every platform. | First CI run (45590617365, Linux x86-64): pixels, detector, crops and routing decisions matched; 24 tests failed after recognition. `rec_latin.onnx` is int8 (QDQ), and ONNX Runtime's x86-64 int8 kernels round differently from arm64's, so characters change ("morning" read as "moning"); fp32 models differ only in the last bits of confidences. LiteParse on that host reads the same way, so this is not a port defect. Recording x86-64 goldens would need the Rust reference built on that host. |
